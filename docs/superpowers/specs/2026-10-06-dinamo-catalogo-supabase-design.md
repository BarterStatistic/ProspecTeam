Un cambio de lista hoy se aplica archivo por archivo. Objetivo: **un cambio de precio o esquema se hace una vez y llega a todos**.

## 4. Esquema

```sql
modelos (
  id                  bigint generated by default as identity primary key,
  nombre              text not null unique,       -- nombre del cotizador, ej. 'HEAVY-B CAB'
  precio_lista        integer not null,           -- sin servicio preventivo
  servicio_preventivo integer not null default 0,
  tipo                text,                       -- 'De trabajo', 'Motoneta', ...
  descripcion         text,
  imagen_url          text,
  activo              boolean not null default true,
  orden               integer not null            -- orden de MODELS en el cotizador
)

esquemas (
  id            text primary key,                 -- 'motonomina', 'credinamo_flex', ...
  etiqueta      text not null,                    -- 'Motonomina', 'Credinamo Flex', ...
  enganche_min  numeric(5,2) not null,
  enganche_max  numeric(5,2) not null,
  unidad_plazo  text not null check (unidad_plazo in ('quincenas','semanas')),
  orden         integer not null
)

esquema_niveles (
  id              bigint generated by default as identity primary key,
  esquema_id      text not null references esquemas(id),
  enganche_desde  numeric(5,2) not null,
  enganche_hasta  numeric(5,2) not null,
  check (enganche_desde <= enganche_hasta)
)

multiplicadores (
  nivel_id  bigint not null references esquema_niveles(id) on delete cascade,
  plazo     integer not null,
  factor    numeric(9,7) not null,
  primary key (nivel_id, plazo)
)

parametros (
  clave  text primary key,
  valor  text not null                            -- ej. ('lista_vigente', '2026-08-25')
)
```

Los plazos de un esquema se derivan de `multiplicadores`; no se guardan aparte. Los 7 esquemas de `SCHEMES` se cargan tal cual (incluido el plazo 144 que solo tiene `motoxpress_flex`).

**Permisos:** RLS activo en las 5 tablas con política `select` para `anon` y `authenticated`. Sin políticas de escritura: solo `service_role` (Table Editor, scripts) escribe.

## 5. Funciones

### `cotizar(p_modelo text, p_esquema text, p_enganche numeric, p_con_servicio boolean default true)`

Devuelve una fila por plazo del nivel aplicable:

| Columna | Cálculo |
|---|---|
| `plazo` | plazo del multiplicador |
| `unidad` | `esquemas.unidad_plazo` |
| `precio` | `precio_lista + (servicio_preventivo si p_con_servicio)` |
| `enganche_monto` | `precio × p_enganche / 100` |
| `a_financiar` | `precio − enganche_monto` |
| `parcialidad` | `round(a_financiar × factor)` |

- Nivel = el de `esquema_niveles` del esquema con `enganche_desde ≤ p_enganche ≤ enganche_hasta`.
- Misma fórmula que `cotizador-pt` (`render`, líneas ~922–949). Para montos positivos `round` de Postgres y `Math.round` de JS coinciden.
- Errores (`raise exception`, mensaje en español): modelo inexistente o inactivo, esquema inexistente, enganche fuera de `[enganche_min, enganche_max]`, enganche sin nivel. Nunca devuelve un número inventado.
- `stable`, `security invoker`, ejecutable por `anon`.

### `catalogo()`

Devuelve un `jsonb` con todo lo que necesita un cliente para cotizar localmente:

```json
{
  "lista_vigente": "2026-08-25",
  "modelos":  [["U2", 21945, 2287], ...],
  "esquemas": { "motonomina": { "label": "Motonomina", "min": 5, "max": 75,
                "termUnit": "quincenas", "terms": [12, ...],
                "levels": [{ "range": [0, 24.99], "m": { "12": 0.101449, ... } }, ...] }, ... }
}
```

Las formas de `modelos` y `esquemas` son **idénticas** a `MODELS` y `SCHEMES` del cotizador (solo modelos activos, en `orden`), para que los clientes cambien la fuente de datos sin tocar su lógica de cálculo. `stable`, ejecutable por `anon`.

## 10. Pruebas

- **Paridad JS ↔ SQL (bloqueante para la fase 3):** script que extrae `MODELS` y `SCHEMES` de `cotizador-pt/index.html`, recorre todas las combinaciones modelo × esquema × nivel (un enganche representativo por nivel, más los bordes `enganche_desde`/`enganche_hasta`) × plazo, con y sin servicio, y compara la parcialidad del JS contra `cotizar()`. Tolerancia: 0 pesos.
- **Forma de `catalogo()`:** su `modelos` y `esquemas` deben ser iguales (deep equal) a `MODELS` y `SCHEMES` del cotizador.
- **Vista `Motos`:** comparar fila por fila contra `motos_legacy`. Diferencias esperadas y únicas: las correcciones de §1, diferencias de ±$1 por truncado vs redondeo, los modelos inactivos/duplicados que ya no aparecen y los 2 modelos nuevos.
- **Errores de `cotizar()`:** modelo inexistente, enganche bajo el mínimo y sobre el máximo devuelven excepción.
- **Clientes:** cada cotizador y Marga se prueban con la red bloqueada hacia Supabase para confirmar el respaldo embebido.

## 11. Riesgos

| Riesgo | Mitigación |
|---|---|
| La fórmula vive en JS y en SQL y podría separarse | Prueba de paridad; cualquier cambio de fórmula exige correrla |
| Supabase pausado o caído | Respaldo embebido en cada cliente; Alex ya depende de este proyecto hoy |
| Un cliente con catálogo viejo embebido | El respaldo solo se usa si falla la red; al publicar una lista nueva se regenera el respaldo en cada cliente (paso del plan) |
| Nombres de modelo cambian y rompen llaves de disponibilidad en Marga | Los nombres se toman del cotizador, que es lo que Marga ya usa |
